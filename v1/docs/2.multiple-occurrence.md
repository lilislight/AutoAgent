# Workflow Runtime 脑暴记录

本文记录阶段性脑暴结论，不代表最终实现。字段、名称和边界仍可在后续设计与实现验证中调整。

通用多发生模型虽然表达能力很强，但 Activation 分组、跨 Trigger Join、Map 展开、Context 并发和完成判断过于复杂，当前决定不采用。

## 1. 总体方向

```text
WorkflowDefinition
    静态、单发生 DAG

Runtime
    执行 Invocation、Node、Command、等待和恢复

Task Runtime
    管理 Child Invocation、TaskHandle、消息和取消
```

核心原则：

- 一个 Invocation 的普通 DAG 中，每个 Node 最多执行一次；
- 普通 Edge 不跨 Invocation，也不会重复激活同一个 Node；
- Map 在一个 Node 执行内部完成并聚合，不扩散为 Workflow 级多发生；
- 动态任务、消息、权限和 Child Workflow 通过 Reference 与 Command 接入；
- 外部事件默认创建新的 Handler Invocation，不直接进入另一个 Invocation 的中间节点；
- 不热修改正在运行的 WorkflowDefinition。

## 2. Session 与 Invocation

```python
Session:
    id: str
    context: SessionContext

Invocation:
    id: str
    session_id: str | None
    workflow_id: str
    context: InvocationContext
    status: "running" | "waiting" | "completed" | "failed" | "cancelled"
```

### Session

Session 表示跨任务的连续性，适合保存：

- 对话历史；
- 用户偏好；
- 长期记忆；
- Artifact 引用；
- Session 下 Invocation 的索引。

Session 不应保存某个运行任务的执行位置、TaskHandle 或临时中间结果。

### Invocation

Invocation 表示一个具体任务的执行身份，适合保存：

- 当前任务目标和 Guidance；
- Node 执行状态和中间输出；
- Wait registration；
- Child Invocation 和 TaskHandle；
- Deadline、取消和恢复状态；
- 固定的 Workflow version。

### 短期与长期 Invocation

每次消息、Webhook 或 API 请求都可以创建一个短期 Invocation：

```text
Event -> Handler Workflow -> Handler Invocation -> Completed
```

只有当一个尚未完成的任务需要跨多次外部事件继续保持执行身份时，才需要长期 Invocation，例如：

```text
长期研究任务
    正在运行 Child Tasks
    等待人工批准
    接收用户的新指导
    可以被取消或恢复
```

长期 Invocation 不是 Server。FastAPI 等 Server 负责接收请求和路由；Invocation 负责一个具体任务的持久生命周期。

### 同一 Session 的并发

长期模型不应假设同一 Session 永远只能有一个运行中的 Invocation：

```text
Session S1
    ├── I1：后台研究任务
    ├── I2：处理用户指导消息
    └── I3：回答另一个独立问题
```

多个 Invocation 不应任意共享同一个可变字典：

```text
Session Context
    使用追加记录、版本化更新或单写协调。

Invocation Context
    每个 Invocation 独立持有。

Mailbox / Event Log
    Invocation 之间通过追加式消息通信。
```

第一版可以限制一个 Session 只有一个前台写入者，但数据模型不应把“只能有一个运行 Invocation”永久写死。

## 3. Node 的单发生语义

```python
NodeExecution:
    id: str
    invocation_id: str
    node_id: str
    status: "ready" | "running" | "waiting" | "completed" | "failed" | "cancelled"
    output: Any | None
    error: Any | None
```

一个普通 Node 在一次 Invocation 中最多创建一个 NodeExecution：

```text
READY
    -> RUNNING
        -> WAITING -> RUNNING
        -> COMPLETED
        -> FAILED
        -> CANCELLED
```

NodeDefinition 不保存运行状态；状态属于 NodeExecution。

`WAITING` 表示该执行已经存在，只是等待 Signal、Task、Approval 或其他外部条件。Signal 唤醒已有的 WAITING 执行，不会创建第二次 Node 执行。

## 4. Map

Map 是 Node 的执行策略，不是 Workflow 级多发生：

```python
Node:
    executable: Callable | Operator | Capability | Workflow
    map_policy: MapPolicy | None
```

```text
MapNodeExecution#1
    ├── MapItemExecution#1
    ├── MapItemExecution#2
    └── MapItemExecution#3
    -> aggregate
    -> complete([result1, result2, result3])
```

- Map Node 只发生一次；
- MapItemExecution 不是普通 NodeExecution；
- Map item 不沿普通 Edge 分别传播；
- 所有 item 完成或形成明确的 item result 后，Map Node 聚合并结束；
- 失败策略、稳定顺序、并发数量和部分成功属于 MapPolicy。

连续 Map 默认形成阶段 Barrier：

```text
MapA 全部完成 -> MapB 全部完成 -> MapC 全部完成
```

如果需要 item 级流水线，可以把连续步骤封装为一个 Map item executable：

```text
Map(
    item -> Rewrite -> Match -> Generate -> Validate
)
```

该 executable 可以是组合 Operator，也可以是独立 Child Workflow。当前不支持共享父 Invocation Context 的 SubWorkflow Map，因为它会重新引入内部 Node 多发生和共享 Context 写冲突。

## 5. SubWorkflow 与 Child Workflow

### 编译期 SubWorkflow

SubWorkflow 只用于结构复用，编译时展开到父 Workflow：

```text
共享父 Invocation
共享 Invocation Context
遵守父 DAG 的单发生规则
```

它不作为运行时 Map 的多实例执行单元。

### Child Workflow

作为 Node executable 调用的 Workflow 创建独立 Child Invocation：

```text
await
    创建 Child Invocation，等待完成，返回 Child output。

spawn
    创建 Child Invocation，可靠持久化后立即返回 TaskHandle。
```

Child Invocation 拥有独立 Invocation Context，可以通过 Mailbox、Command 或受控共享资源与父任务通信。

## 6. Map 与 Spawn

Map 和 Spawn 是两个正交维度：

```text
Map
    这个 Node 对多少个 item 执行。

await / spawn
    每个 Child Workflow 调用等待到哪里。
```

| Map | Child 调用方式 | Node 完成条件 | Node 输出 |
|---|---|---|---|
| 无 | `await` | Child 完成 | `Output` |
| 无 | `spawn` | Child 可靠创建 | `TaskHandle` |
| 有 | `await` | 所有 Child 完成 | `list[Output]` |
| 有 | `spawn` | 所有 Child 可靠创建 | `list[TaskHandle]` |

`map + spawn` 的过程：

```text
TaskSpec list
    -> MapSpawn NodeExecution
        ├── create Child#1 -> Handle#1
        ├── create Child#2 -> Handle#2
        └── create Child#3 -> Handle#3
    -> complete([Handle#1, Handle#2, Handle#3])
```

它等待所有 Child 被可靠创建，不等待 Child 运行结束。部分创建成功不能被隐式回滚，结果必须保留成功 Handle 和失败信息，再由显式后续节点决定取消、重试或接受部分成功。

## 7. Reference 与 Command

Runtime 对象以可序列化 Reference 在 Workflow 中流转：

```text
TaskHandle
WorkflowRef
CapabilityRef
PermissionGrant
WaitRef
```

Command Node 操作这些 Reference：

```text
SpawnWorkflow
AwaitTask / AwaitAnyTaskEvent
GetTaskStatus
SendTaskMessage
ReplyTaskQuestion
CancelTask
AwaitSignal / SendSignal
UpdateGuidance
InterruptCurrentOperation
BindCapability
RequestApproval
```

Command 是 Node 的一种 executable。动态对象作为输入传给已经存在的 Command Node，不会动态增加 Node 或 Edge。

## 8. 外部事件与 Handler Workflow

当前不引入 ReactiveScope。消息、Webhook、Timer、Child Event 等语义事件默认调用普通 Handler Workflow，并创建新的短期 Invocation：

```text
External Event
    -> Event Router
    -> Handler Workflow
    -> Handler Invocation
    -> Command(target_invocation_id)
```

例如用户实时调整长期任务：

```text
Message Handler Invocation
    -> ValidateMessage
    -> SendTaskMessage(target=I1)
    -> UpdateGuidance(target=I1)
    -> InterruptCurrentOperation(target=I1)  # 必要时
```

长期任务应用消息有三种边界：

```text
边界式
    当前 Operator 完成后，在下一安全边界读取 Mailbox。

协作式
    长时间 Operator 主动检查控制消息。

中断式
    Command 取消当前 Operator，再使用新 Guidance 继续或重启。
```

所谓实时，是消息立即可靠送达；已经发出的不可中断调用不能被直接修改，只能等待边界或取消重启。

## 9. Mailbox、Signal 与 Wait/Resume

Mailbox 持久化消息；Signal 用于恢复已存在的等待点：

```text
Main Invocation:
    A -> AwaitSignal -> B

Handler Invocation:
    Receive Event -> WriteMailbox -> SendSignal
```

运行过程：

```text
AwaitSignal NodeExecution
    -> 注册等待条件
    -> WAITING

Signal 到达
    -> 写入持久 Mailbox/Event Log
    -> 匹配 Wait registration
    -> 恢复同一个 AwaitSignal NodeExecution
    -> COMPLETED
    -> 沿普通 Edge 到达 B
```

检查 Mailbox 和注册 Wait 必须原子完成，或者使用单调 sequence/cursor，避免 Signal 在注册前到达而丢失。

Signal 不会直接激活 Invocation 中任意 Node，也不会创建第二条主 DAG。

## 10. 父子任务通信

父任务通过 TaskHandle 查询和控制 Child：

```text
GetTaskStatus(handle)
AwaitTask(handle)
AwaitTaskEvent(handle, cursor)
SendTaskMessage(handle, message)
CancelTask(handle)
ReplyTaskQuestion(handle, question_id, answer)
```

子任务可以：

```text
SendParentMessage
AskParent(question)
AwaitParentReply(question_id)
```

典型协议：

```text
Child AskParent
    -> Parent Mailbox/Event Log

Parent Handler Invocation
    -> Decide
    -> ReplyTaskQuestion

Child AwaitParentReply
    -> resumed
    -> Continue
```

消息和事件至少需要：

- 稳定 command id，避免命令重试产生重复副作用；
- 单调 sequence/cursor，读取尚未消费的事件；
- question id，关联请求与回复；
- acknowledgement，区分发送、接收和应用；
- ownership/permission，限制谁能控制 Child。

## 11. Node 输出行为

普通 Operator 返回一次最终结果：

```text
execute(input) -> output
Runtime 将其解释为 complete(output)
```

支持流式输出的 Operator 可以：

```text
emit(port, value)      零次或多次，不结束 NodeExecution
complete(value | None) 最多一次，正常结束
fail(error)            失败结束
cancel(reason)         取消结束
```

所有 Operator 最终必须进入 `completed`、`failed` 或 `cancelled`。即使没有业务完成值，也应当 `complete(None)`，不能在最后一次 emit 后直接消失。

## 12. Edge 事件选择

Edge 不读取一个可反复扫描的“Node 当前状态”，而是响应 NodeExecution 的确定状态转换或 Emission：

```python
Edge:
    source: str
    target: str | HandlerWorkflowRef
    source_event:
        "completion"
        | "failure"
        | "cancellation"
        | EmissionPort
    condition: Condition | None
```

不必为每种行为定义完全不同的 Edge 类型；`source_event` 明确它监听什么。

### Completion Edge

```text
A COMPLETED(output) -> B
```

这是普通 DAG 的正常传播边，携带最终输出。

### Failure Edge

```text
A FAILED(error) -> HandleError
```

Failure Edge 只在 Node 的 Retry 和等价 Fallback 已经结束、NodeExecution 确认进入 FAILED 后触发，不响应每次内部 Attempt 失败。

### Cancellation Edge

```text
A CANCELLED(reason) -> Cleanup
```

局部 Node 取消可以进入受控清理路径。Invocation 全局取消时，默认停止普通业务传播，只运行受控 Finalizer，避免取消边再次启动无限业务流程。

### StreamEdge

```text
A emit(port="progress", value)
    -> StreamEdge
    -> 外部 Output 或 Handler Workflow
```

在单发生 DAG 中，一次 NodeExecution 的多个 Emission 不能反复激活同一 Invocation 内的普通 Node，否则会重新引入通用多发生。因此 StreamEdge 第一阶段只允许：

```text
1. 发布为 Invocation/Workflow 的外部流式输出；
2. 写入 Event Log、Trace 或 Mailbox；
3. 调用 Handler Workflow，每次 Emission 创建新的 Handler Invocation。
```

暂不允许：

```text
StreamEdge -> 当前 Invocation 的普通中间 Node
```

只用于 UI 的 Token Chunk 可以直接输出，不必进入 Workflow 调度。Tool Call、结构化对象等语义 Emission 才适合通过 StreamEdge 调用 Handler Workflow。

## 13. Edge Condition 与 Route

不同 source event 提供不同 Condition 输入：

```text
completion：final output
failure：error 和 attempt summary
cancellation：reason 和 initiator
emission：port、sequence 和 value
```

Condition 只负责：

```text
condition(event, readonly_context) -> bool
```

它不能重试 Operator、修改 Context、取消 Child 或执行副作用。

同一个 source event 可以匹配多条出边。当前默认行为仍是 `all-match`；其他 RoutePolicy 暂不定义。

## 14. Retry、Fallback 与 Failure Edge

三者职责不同：

```text
Retry
    再次尝试同一个逻辑操作，仍属于同一个 NodeExecution。

Capability Fallback
    切换到输入输出契约和业务语义等价的 Operator，
    仍试图完成同一个 NodeExecution。

Failure Edge
    NodeExecution 已经最终失败，Workflow 改走另一条业务路径。
```

推荐顺序：

```text
Attempt failed
    -> Retry / equivalent Fallback
    -> still failed
    -> NodeExecution FAILED
    -> Failure Edge
```

业务语义发生变化时，不应隐藏在 Operator Fallback 中：

```text
自动处理失败 -> 人工审核
```

应当使用显式 Failure Edge。

NodeExecution 一旦产生会驱动业务行为的语义 Emission，默认不允许透明 Retry，否则可能重复执行下游副作用。只有具备稳定 Emission id、Cursor 和幂等重放能力时才能开放。

## 15. DAG + Command 的能力边界

可以实现：

- 普通确定性 Workflow；
- Node 内 Map 并行和聚合；
- Child Workflow 的 await/spawn；
- TaskHandle 的查询、等待、通信和取消；
- 用户消息、Webhook、审批和 Child Event 的 Handler Workflow；
- Mailbox、Signal、Wait/Resume；
- 运行中的 Guidance 更新和显式 Interrupt；
- 动态 Capability、Permission 和 WorkflowRef 绑定；
- Node 流式输出到外部或 Handler Invocation；
- 同一 Session 多个独立或协作的 Invocation。

不能自然实现：

- 在 Workflow 图上展开可重复的 Agent Think/Act Loop；
- 多个 Stream Emission 在同一 Invocation 内反复经过普通 Node 链；
- 无 Barrier 的跨 Node item 级 Map Pipeline；
- 外部事件直接从当前 Invocation 的任意中间节点创建新执行链；
- 任意跨 Trigger Join；
- 运行时修改活跃 WorkflowDefinition。

这些限制可以通过以下方式处理：

```text
Agent Loop
    先封装在 Agent Operator；未来必要时增加受控 LoopScope。

Item Pipeline
    放入一个 Map item executable，或使用独立 Child Invocation。

事件处理
    每个事件创建 Handler Invocation，通过 Command 影响长期任务。

流式处理
    在 Operator 内处理，或由 StreamEdge 启动短 Handler Invocation。
```

## 16. 当前建议的实现顺序

```text
1. 单发生 DAG、NodeExecution 和 completion edge
2. Condition、默认 all-match 与普通多入边
3. Node 内 Map、并发、稳定排序和聚合
4. failure edge、基本取消和 Finalizer
5. Wait registration、Mailbox、Signal 与恢复
6. Child Invocation、TaskHandle、await/spawn
7. Handler Workflow 与跨 Invocation Command
8. Session 多 Invocation 和受控 Session Context 更新
9. Node emit、外部流式输出与受限 StreamEdge
10. Retry、Fallback、权限和监督策略
```

当前不先实现通用多发生、ActivationGroup、共享 Context 的 SubWorkflow Map、ReactiveScope 或动态 Workflow 图。

## 17. 后续需要确定的问题

- 普通多入边在 Condition 分支下如何确认不可达路径；
- MapPolicy 的部分失败、取消、结果类型和稳定顺序；
- `map + spawn` 部分创建成功时的默认结果结构；
- Handler Workflow 的路由、幂等和权限；
- Invocation 间 Command 的一致性、确认和超时；
- 长期 Invocation 的 idle timeout、close 和资源清理；
- Session Context 的追加、版本控制和单写协调方式；
- Cancellation Edge 与 Finalizer 的明确边界；
- Emission 的持久化级别、sequence、背压和重放；
- StreamEdge 启动 Handler Invocation 时的速率限制与失败处理；
- Agent Loop 是否最终需要显式、受控的 LoopScope。
