# Runtime Session

A Runtime Session is durable state for one Workflow context.

It is not one call. It can contain many Runtime Runs over time.

## Purpose

Runtime Sessions solve the chatbot-style problem: one incoming message creates
one Runtime Run, but the conversation history must survive across many messages.
The stable `session_key` connects those runs to the same session.

```text
session_key = conversation_id
Runtime Session = conversation state
Runtime Run = one incoming message execution
```

If no session key is provided, Runtime creates a fresh session and the behavior
is similar to an ordinary one-off script execution.

## Model

```python
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Any


@dataclass
class RuntimeSession:
    id: str
    workflow_id: str
    workflow_version: str
    session_key: str

    lifecycle: str
    context: "RuntimeContext"

    current_run_id: str | None = None
    run_ids: list[str] = field(default_factory=list)

    metadata: dict[str, Any] = field(default_factory=dict)
    created_at: str | None = None
    updated_at: str | None = None
```

## What Belongs Here

A Runtime Session may store:

- durable context shared by runs
- session lifecycle state
- run index for the session
- active run pointer or lock owner
- session-level metadata
- event log references
- aggregate resource usage

A Runtime Session should not store static Workflow IR fields such as graph
indexes, compiled conditions, or capability descriptors.

## Session Key

`session_key` is supplied by the caller or generated by Runtime.

The key is the practical boundary for reuse:

```text
same workflow + same session_key -> same Runtime Session
same workflow + no session_key -> fresh Runtime Session
```

Runtime may normalize this into an internal session id, but external callers
should not need to know that id before the first invocation.

## Default Concurrency

The first design should serialize runs within the same Runtime Session. That
keeps session context writes predictable.

Different Runtime Sessions may run in parallel because their run state and
session context are isolated.
